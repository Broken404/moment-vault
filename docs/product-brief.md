# 产品落地草案

日期：2026-10-19。状态：需求草案，未开始扩展实现。本文中的范围和交互建议不代表用户已经确认所有细节。

推进顺序补充：已按用户要求建立 GitHub 仓库，当前共同完善方案，暂不开始扩展实现。

当前讨论进度：视频部分暂按现有方案保留。图片收集入口采用悬浮球扇形菜单，用户已确认粘贴或拖入后直接保存草稿箱并反馈结果；当前细化接收反馈，内置截图后续评估。

最新决定优先于下文的早期建议：入口采用网页内悬浮球与快捷键；所有素材首先进入草稿箱，审核通过后才到资产库；视频由用户手动开始和结束录制，停止后直接把实际视频文件存入草稿箱。按用户要求，目前只逐点明确安装后的第一步，不展开全流程。详见 [悬浮球入口与首次使用](entry-and-first-use.md)。

## 1. 已确认需求

- 首批平台：B站、YouTube、X（Twitter），主要入口考虑 Edge 浏览器扩展；用户也希望考虑 Codex 接入。
- 能保存截图、视频时间点和短视频片段。
- 日常展示采用网页内悬浮球与快捷键，避免用户每次进入扩展管理页寻找入口。
- 点击悬浮球，以扇子打开的效果展开三个入口：屏幕录制、设置、接收截图。非支持平台保留屏幕录制入口但置灰，提示仅支持 B站、YouTube、X。
- 悬浮球覆盖所有普通网页，方便收集截图等素材；视频录制功能仅限 B站、YouTube 和 X。全站入口不等于全站视频录制。
- 图片部分优先解决收集入口，让已有截图或图片方便地进入草稿库；内置截图后续评估。
- 点击“接收截图”后，接收区域自动获得焦点，支持直接 Ctrl + V 粘贴和拖入图片；自动保存到草稿箱并反馈结果，成功显示缩略图和“已存入草稿箱”，不增加一次保存确认。
- 视频采集需要预录制选段模式：起点与终点可拖动、可通过方向键调整；较小的预览窗跟随被调整端点显示对应画面，通过独立按钮预览整个片段。按键步长初步为方向键 5 秒、Ctrl + 方向键 1 秒。
- 预览窗采用网页内可调整大小的悬浮窗，不另开新窗口。预录制模式可打开和关闭，关闭后恢复进入前的观看位置，便于继续正常观看。
- 所有素材先进入草稿箱，经过人工和 AI 分类、挑选及审核后进入资产库，各种入口都不能跳过草稿阶段。
- 视频由用户手动开始、手动结束录制，不进行隐蔽的后台录制。草稿箱直接保存可查看的实际视频文件，不能只保存链接、时间点或缩略图来替代片段。
- 设置中分别选择草稿箱和资产库的本地目录，配置界面语言、方向键时间步长与 Ctrl + 方向键时间步长；默认步长为 5 秒和 1 秒，均可修改。详见 [设置界面草案](settings.md)。
- 设置中已确认加入快捷键管理、悬浮球外观（大小、透明度、恢复默认位置）与恢复默认设置；恢复默认不删除素材或清空、改变目录选择，具体默认值继续细化。
- 资产方向不受限制。产品服务于 AI 时代的灵感、创意与其他个人积累，不能预设为某一职业或某一种创作用途。
- 目标是落地成真实自用产品，并成为用户的第一个 GitHub 开源项目。

## 2. 产品主张与待验证假设

建议主张：记录有意义的瞬间，把它变成可找到、可理解、可再次使用的个人资产。

一个记录单元是一个“瞬间”，可以包含图片、文字、视频片段和时间位置。同一视频或帖子可以产生多个瞬间，不能只按来源链接去重。

值得验证的假设：

1. 自动保留来源、时间位置和一句收藏理由，能降低日后重新理解素材的成本。
2. 采集与整理分时进行，更适合观看、阅读和浏览中的灵感捕捉。
3. 草稿与正式资产分开，能帮助用户形成可靠的个人选择，而不只是增加收藏量。
4. 统一整理三个平台的内容，比在各个平台分别收藏更便于后续查找和交给 AI 使用。

这些是产品假设，尚无用户实验或竞品研究证明，暂不声称独创或市场差异已经成立。

## 3. 推荐入口

第一步做 Edge 扩展，负责用户主动触发的采集和本地资产管理。Codex 后续作为整理与调用入口，共享同一份资产及状态，不再建立一份互不相通的库。

第一版以本地保存为默认建议，降低首次使用的配置负担；它并不意味着数据天然永久安全，必须提供可恢复的备份。

## 4. 两个核心场景

### 视频瞬间

视频的当前原则：用户手动开始录制、手动结束录制，结束后直接保存实际视频文件到草稿箱，后续在草稿箱中查看与审核。此前确认的起终点选择和预览体验继续保留；它们如何与手动录制衔接，后续单独讨论，不引入按区间自动开始或自动结束录制。

用户已明确需要类似剪辑软件的时间线选段体验。预览窗口比原网页播放器小，调整端点时主预览画面随之定位，另点按钮播放整个选区。起点、终点与预览播放头分别表达区间边界和当前画面；建议键盘修改当前选中的端点。详细的已确认要求、建议与待定项见 [视频选段与预录制交互](video-range-selection.md)。

预览界面为当前网页内可调整大小的悬浮窗，预录制模式可随时开关。用户已确认关闭后回到进入前的观看位置。建议进入时暂停原视频，退出时恢复原播放/暂停状态；关闭必须停止试播、定位和快捷键接管，让用户恢复正常观看。

必须让用户分清三件事：

- 标记时间：留下当前播放位置，无须假装已经拿到视频文件。
- 录制接下来的片段：用户开始、停止录制，获得实际媒体文件；刚刚过去的内容需要先回放。
- 保存刚刚过去的片段：需要事先采集内容；当前不规划持续后台缓冲录制，采用用户明确手动开始和结束的采集原则。

动态预览和实际视频保存分别验收，暂不承诺帧级裁切。选段预览不会启动录制；实际录制的开始与结束必须来自用户明确操作，时间线终点不作为自动结束录制的既定规则。

### 观点或视觉瞬间

已确认图片部分以收集入口为重点：通过悬浮球扇形菜单打开“接收截图”，Ctrl + V 粘贴或拖入图片后直接保存到草稿箱并反馈结果。成功时显示图片缩略图及“已存入草稿箱”；失败时保留图片并允许重试。来源、备注与分类可稍后补充，不阻塞本次接收。选择本地文件作为补充入口建议，内置框选截图后续评估。保存选中文字保留为另一种候选输入方式。

外部图片不自动绑定当前网页。当前页面只作为可确认的来源候选；来源留空不阻塞草稿保存。图片导入时间与实际截图发生时间分开，不把当前视频位置伪装成截图时间点。详见 [图片与截图导入草案](image-intake.md)。

X 的来源应尽可能关联具体帖子，而不是只保存首页、搜索页或作者主页。截到多条帖子时应允许用户选择来源，识别不确定时明示并允许手填。

## 5. 采集与整理分开

采集面板保持轻量：预览、来源、可选的一句话备注、保存结果。不要让用户在灵感出现时填写复杂分类表。

整理页面展示草稿队列、原始媒体、来源、用户理解和 AI 建议。可集中处理多条草稿，但不能用批量生成内容掩盖尚未人工确认的状态。

建议的最小状态：

- 草稿：已保存，可继续编辑和补充附件。
- 正式资产：用户明确确认入库，可撤回为草稿。
- 已放弃：可恢复，永久删除为单独操作。

AI 建议单独保存，不另造一个容易混淆的“AI 已审核即正式入库”状态。未运行、运行失败和没有建议必须可区分。

## 6. 每条资产保留什么

| 信息 | 用途 | 要求 |
| --- | --- | --- |
| 原始附件 | 实际截图、文字或录制片段 | 保存成功后才显示已采集；附件类型不等于主题分类 |
| 来源快照 | 平台、来源链接、当时标题、可识别的作者、采集或导入时间 | 不确定的字段留空或让用户补充；外部图片的当前网页仅作候选，导入时间不等于截图发生时间 |
| 视频位置 | 来源视频标识、分集/分P标识、时间点或区间 | 与实际录制时长、录制时间分开记录 |
| 用户理解 | 为什么收藏、值得借鉴什么、可能如何使用 | 采集时可跳过，整理时引导补充 |
| 自由标签 | 用户自己的组织方式 | 标签可编辑，不预设唯一的分类体系 |
| AI 建议 | 标签、摘要、识别文字、潜在用途 | 与原文和用户批注分开，保留生成状态和来源 |
| 入库记录 | 当前状态、人工确认时间 | AI 建议不能自动改变为正式资产 |

“转场”“观点”“构图”等可作为用户自定义标签或示例，不做不可更改的顶层类别。来源失效后，仍可查看已经落地的附件、来源快照及用户理解。

## 7. 第一版建议范围

第一版目标是跑通“采集 → 草稿 → 整理 → 正式资产 → 找回 → 导出与恢复”。

- 网页内悬浮球与快捷键作为日常入口；统一草稿箱和审核后的资产库。
- 图片入口优先建议粘贴导入，并支持拖入与选择本地图片文件；内置网页截图、框选裁剪后续评估。网页文字保存与来源记录另行细化，外部截图来源需用户确认。
- 视频采用可拖动起终点、键盘调整、边界动态预览与整段预览的选段流程；使用可调整大小的网页内悬浮窗，关闭模式后恢复进入前的观看位置。B站与 YouTube 普通视频页优先验证区间采集；X 视频同样纳入验证，未通过前不标记为支持。
- 支持手动导入已有图片或片段，作为来源无法直接采集时的明确补充入口。
- 人工编辑标题、理解、自由标签；入库、撤回和放弃。
- 关键词、标签、平台、媒体类型与状态筛选；正式资产中能找回之前保存的瞬间。
- 媒体与元数据一起导出，并能从备份恢复；只导出索引不算完成。

AI 是完整产品方向的一部分。建议在采集与保存可靠后接入第一条真实的 AI 整理流程，不把伪造建议或静态演示称为 AI 功能。若首个可发布版本只完成手动整理，必须明确标注其范围与 AI 计划。

暂缓：账号系统、云同步、团队共享、手机端、全屏幕采集、复杂知识图谱。不规划持续后台录制或绕过草稿审核的自动入库。

## 8. 三个平台的覆盖必须逐项证明

| 平台 | 优先验证 | 必须防止的问题 |
| --- | --- | --- |
| B站 | 普通视频、时间位置、截图与短片 | 分P/分集错位、播放器切换后旧来源残留 |
| YouTube | 普通视频、时间位置、截图与短片 | 把广告位置误当正文位置、站内导航后抓到旧视频 |
| X | 具体帖子关联、文字与截图，再验证视频 | 抓错帖子、线程内来源不明、多视频选择不明 |

Shorts、直播、弹窗视频、跨域嵌入、全屏播放、登录状态和受保护媒体列为独立测试项。支持一个普通视频页不能外推为整个平台所有形式均支持。

## 9. 实现方向建议

浏览器扩展采用 Manifest V3；扩展内独立页面承载完整资产库，采集入口保持轻量。

三个平台分别负责提取来源与视频位置，共用保存、整理、检索与备份逻辑。平台变化应集中在相应的提取实现内。不要为尚未存在的云服务或多种数据库先搭复杂抽象。

按用户最新确定的目录要求，原始素材与必要元数据应落到分别选择的草稿箱或资产库本地目录；优先验证目录授权、写入和跨站共用的实现路线。IndexedDB 可用于句柄、索引、设置和必要临时数据，不再作为媒体最终只保存在浏览器内部的既定方案。实际完成指定目录写入后才能显示保存成功。

保存必须应对空间不足、写入中断、重复点击与扩展关闭；保存失败不能显示成功。录制文件、原视频时间范围与录制质量应如实记录。

AI 接入前，先让用户知道哪些内容会发送给哪个服务；未启用 AI 时，采集、整理和访问已有资产仍应可用。搜索结果、来源文本和模型建议均不能被当作执行指令。

## 10. 推进与验收

### 第一步：验证采集技术

验证外部截图粘贴、拖入和文件选择后的预览与保存；用自制测试页验证视频时间点、带声音录制、停止保存与播放。再在 Edge 中逐个平台验证，并记录浏览器版本、页面类型、操作步骤和实际结果。内置截图不作为当前建议路线的前置条件。

### 第二步：完成可用闭环

采集一条截图、一条文字和一条真实短片，均能在重启浏览器后查看；在草稿库补充理解并入库；能从正式库查找；导出后在空白测试环境恢复全部附件和状态。

### 第三步：加入 AI 整理

AI 为真实草稿给出可编辑建议，保留原始内容。用户能接受或拒绝建议；拒绝不改变原文；AI 运行失败不影响已经采集的素材；人工确认前保持草稿。

### 第四步：形成开源发布

仓库从规划阶段开始建立。软件发布前补齐安装说明、实际支持矩阵、已知限制、隐私与数据流说明、关键自动化检查和可复现人工验收。用自制示例录制演示，再确定名称、许可证并发布首个可安装版本。

Git 历史来自实际完成的变更，不回填历史或为了显得成熟制造提交。代码、声明的功能和演示效果保持一致。

建议自用验证：先积累约 20 条不同主题的真实草稿，隔几天尝试重新找回并实际复用几条。记录哪些内容能保存却无法理解、哪些来源容易错配、哪些整理步骤最拖沓，再决定优先修什么。
