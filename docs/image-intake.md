# 图片收集入口草案

更新日期：2026-10-19。状态：图片接收后直接保存草稿箱并反馈结果已确认，具体视觉样式仍在细化；尚未实现或验证。

## 当前讨论

视频部分暂按现有方案保留。用户提出已有截图工具可以完成截图和复制，并进一步确认“主要是收集入口的问题”。

已确认的方向：优先让已有图片方便地进入草稿资产库，复用用户的截图习惯。内置框选截图后续再评估，不视为永久取消截图能力。

用户进一步明确：点击“接收截图”入口后，能直接 Ctrl + V 粘贴图片，也能拖入图片。两种输入方式作为接收入口的明确需求。

已确认：图片粘贴或拖入后直接保存到草稿箱并反馈结果，不要求用户再点击一次保存。成功时显示图片缩略图和“已存入草稿箱”，不代表审核通过或进入资产库。

## 首版建议

优先完成图片接收与保存，以粘贴为主入口，拖入文件和选择本地文件作为补充。内置框选截图后续再评估。

当前确定的接收操作：使用现有工具截图并复制 → 点击“接收截图” → Ctrl + V 或拖入图片 → 自动保存到草稿箱并反馈结果。来源和备注可随后补充，不作为本次保存的前置步骤。

图片导入可服务于各类灵感与内容，建议不限定为 B站、YouTube 和 X 的截图；这三个平台继续是视频适配和网页来源识别的首批重点。

## 最小交互

- 点击“接收截图”后，在当前网页展开小型接收区域，提示“Ctrl + V 粘贴图片，或将图片拖到这里”。接收区域自动获得输入焦点，不要求用户再点一次输入框才能粘贴。
- Ctrl + V 接收剪贴板中的图片并显示预览；拖动图片进入接收区时高亮，放下后显示图片预览。本地图片文件拖放与网页图片元素拖放需分别验证。
- 粘贴或拖入后显示真实图片预览及保存状态。保存原始图片文件，预览缩略图不能替代原图。
- 标题、来源链接和一句备注都可稍后补充；不在收图时强制分类、OCR 或 AI 分析。
- 用户粘贴或拖入即触发草稿保存，不需要二次确认；图片与草稿记录均落地成功才显示“已存入草稿箱”。该操作不进入资产库。
- 保存后继续使用原网页，不接管网页输入框里的正常粘贴，也不在用户未操作时持续读取剪贴板。
- 拖入图片文件与从网页拖动链接/图片元素分开处理；图片链接不等于已经拿到图片文件，失败时提供选择本地文件的入口。
- 粘贴与拖放的接管限定在激活的接收区域；关闭后释放输入焦点和事件接管。图片拖入该区域时避免触发浏览器默认跳转打开图片，区域外的网页交互保持正常。

默认是一图一条草稿还是一条草稿允许多图、收图面板采用何种布局，留待后续讨论，不在本轮擅自锁定。

## 收集入口的当前决定

入口的重点是少切换、容易粘贴、明确知道图片是否已存入草稿。建议图片收集无需先开启视频预录制模式。

用户已确定日常展示形式为网页内悬浮球配合快捷键，取代此前“侧栏还是浮层”的入口待选建议。展示范围已经确认，首次提示和悬浮球点击后的面板内容分开逐项细化，见 [悬浮球入口与首次使用](entry-and-first-use.md)。

展示范围已确认是所有普通网页，方便在其他网页也放入截图；只有视频录制限定在 B站、YouTube、X。具体首次提示与悬浮球操作继续逐点讨论。

接收图片的已确认入口路径：点击悬浮球 → 扇形展开菜单 → 点击“接收截图”。此入口在普通网页可用，不依赖该网站是否支持视频录制。接收界面的布局和保存交互继续分别细化。

保存方式已确认：接收到图片后直接保存草稿箱并显示结果，取代早期“先预览再点击保存”的流程建议。是否提供即时撤销，以及误收后的具体处理，后续单独确定。

无论最终保存交互如何，所有图片先进入草稿箱，不能绕过审核直接成为正式资产。

## 接收反馈

用户已明确接收操作必须有反馈，且已确认直接保存草稿箱。建议反馈直接出现在接收区域，不使用需要额外点击关闭的成功弹窗。

| 情况 | 建议反馈 | 成功含义 |
| --- | --- | --- |
| 图片拖到接收区域上方 | 区域高亮，提示“松开即可添加” | 仅表明此处可以接收，尚未保存 |
| 粘贴或放下图片后 | 显示图片预览与“正在保存到草稿箱…” | 已开始处理，尚未确认保存成功 |
| 原图与草稿记录保存成功 | 勾选标记、图片缩略图与“已存入草稿箱” | 已可从草稿箱查看，仍未进入资产库 |
| 剪贴板没有可用图片 | “未检测到图片，请复制图片后再试” | 不生成空白草稿 |
| 图片格式无法处理 | 明确说明无法接收这张图片，允许重新粘贴或选择文件 | 不将图片链接或文字冒充已保存图片 |
| 保存失败 | “保存失败，图片尚未存入草稿箱”，显示具体原因和“重试” | 保留当前图片预览及已填内容，不显示成功 |

反馈原则：

- 图片缩略图出现不代表保存完成；成功文案必须等待实际原图与草稿记录写入完成。
- 成功状态同时使用文字和图形，让用户知道保存了哪张图片；成功提示可以简短，不自动强制跳转到草稿箱。
- 失败反馈保持可见，供用户重试；不能仅闪过后消失，也不能把失败图片显示成已存入。
- 处理速度快时不为动画强制延迟保存；耗时较长时保留清楚的处理中状态，不伪造百分比。
- 本轮只确定接收与保存反馈，不同时展开草稿审核或资产库管理。

## 来源信息

外部截图的可靠出处需要用户提供或确认。导入时不能假设当前网页就是图片的来源，也不能把 OCR 或模型推断当作已经确认的事实。

建议采用三种清楚的情况：

| 情况 | 处理方式 |
| --- | --- |
| 用户确认来自当前网页 | 附上当前页面链接；识别到的标题、作者等继续按实际可靠程度处理 |
| 来自其他网页或软件 | 用户可以补链接或文字来源说明 |
| 暂不清楚或不想填写 | 留空或标记来源未确认，仍可保存草稿 |

当前网页只作为来源候选，不能静默写成图片的真实出处。记录导入时间；截图实际发生时间未知时留空。当前视频播放位置也不能直接当作截图中的视频时间。

## 技术依据与待验证事项

浏览器的 `paste` 事件响应用户主动粘贴；`ClipboardEvent.clipboardData` 提供剪贴板数据，文件类型的 `DataTransferItem` 可通过 `getAsFile()` 取得文件对象。文件拖放使用 `dragover` 与 `drop` 等事件处理。见 [MDN paste](https://developer.mozilla.org/en-US/docs/Web/API/Element/paste_event)、[clipboardData](https://developer.mozilla.org/en-US/docs/Web/API/ClipboardEvent/clipboardData)、[getAsFile](https://developer.mozilla.org/en-US/docs/Web/API/DataTransferItem/getAsFile) 和 [文件拖放](https://developer.mozilla.org/en-US/docs/Web/API/HTML_Drag_and_Drop_API/File_drag_and_drop)。

建议先验证用户主动 Ctrl + V 的路径，再判断是否需要额外的“读取剪贴板”按钮。不能把浏览器文档能力当作 Edge 扩展页面或网页内面板已经实测成功。

需要区分剪贴板中的实际图片、文件对象、HTML、图片链接和纯文本。来自不同截图工具、复制本地文件或复制网页图片时，数据形式可能不同；首版支持范围必须实测记录。

验收重点：

1. 用现有截图工具复制图片，点击“接收截图”后无需再点输入框，Ctrl + V 后自动完成草稿保存并反馈结果，不需要再按保存。
2. 导入图片文件能通过拖入与文件选择完成；保存后重启仍可查看原图。
3. 剪贴板没有可用图片时有明确反馈，不创建空白草稿；备注框中粘贴文字保持正常。
4. 从其他页面或软件复制图片，不会错误绑定当前网页或当前视频时间。
5. 保存失败时保留当前图片预览和用户备注，允许重试；不能显示成功。
6. 导出和恢复包含实际原图、已确认来源、备注与草稿状态。
7. 拖入接收区域时有高亮反馈，放下图片后出现预览；原网页不因这次拖放跳转到图片文件。
8. 保存完成前不显示“已存入草稿箱”；完成后显示对应缩略图与成功文案，文件确实可以在草稿箱查看。
9. 模拟保存失败时，图片保留、错误清楚且可重试，不出现成功反馈或空白资产。

## 何时重新评估内置截图

自用时观察“截图 → 切到插件 → 粘贴”的操作成本。如果频繁出现错过画面、切换繁琐，或需要在截图瞬间可靠保留网页来源及视频时间，再评估一键截图或框选截图。

这是体验取舍，不是对截图工具市场的完整调研。本轮没有新增截图或图片导入代码。
