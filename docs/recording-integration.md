# 正式录制与 MP4 保存联动

2026-10-23：正式扩展与新开发助手的实际录制到 MP4 草稿已打通。真实 YouTube 样本完成到 B 自动停止、快捷键提前结束及录制中关闭模式三条保存路径。随后优化启动和停止时序，同一 2～4 秒选区的 MP4 容器余量从约 0.508 秒降至 0.101 秒。后续文件仍有约 0.077～0.151 秒波动，一段长选区超过本轮 0.12 秒比较门槛；不记为精度全部通过。旧短片停帧单独保留为未解决质量项；这些样本不代表三站完整验收或逐帧精确裁剪通过。

## 用户流程

从桌宠的“屏幕录制”进入，在原时间条上选择 A/B，通过独立窗口确认边界。页面按钮只负责选段和预览；真正录制必须按 Edge 分配给正式扩展的录制快捷键。若试验扩展先占用相同快捷键，需要在 `edge://extensions/shortcuts` 给正式扩展重新绑定，关闭试验版不保证自动转移绑定。

开始前先检查目录和配套视频工具，定位 A 并锁定来源、位置和视口。持久化任务后，确认 `MediaRecorder.start()` 已同步进入 recording 即播放源视频，不再等异步 start 事件；保留不阻塞播放的启动超时保护。状态保存与通知不阻挡开始播放、暂停和停止采集。到 B 暂停并自动结束，也可用同一快捷键或“结束并保存”提前结束。关闭模式先停止采集并等待最后一块落入本地暂存，再恢复观看；MP4 转换在后台继续，不让用户等待转换才退出。

录制时隐藏桌宠、选段窗口、A/B 与目标播放器的原生控制条；小状态条放在视频外。准备时先渲染，按实际尺寸重新定位后检查交叠，文字限制为单行，防止状态变化撑高。当前只支持一项正在录制或保存的任务。页面隐藏、来源改变、播放器或视口移动会结束当前片段，避免继续采集错误区域；完整视频必须处于可见范围。

## 模块与恢复边界

- 服务工作线程只在实际扩展命令中获取标签页采集 ID，协调准备、录制、停止和保存状态。普通网页不能通过消息启动采集。
- Offscreen 页面拥有标签音视频流，以 Canvas 裁剪视频区域并保留标签声音。录制路线延续既有基线，没有将它描述为旧停帧的根因修复。
- MediaRecorder 每 500 ms 形成 WebM 块，按序写入扩展 IndexedDB。上传按 192 KiB 分片，逐片等待助手确认；丢失确认后沿用同一上传和分片标识，重复请求必须字节一致。没有一次拼接整段视频的内存缓冲。
- 收到最后一块后释放采集资源，再异步上传和转换；本地助手从自己的 `media` 目录取 FFmpeg/ffprobe，检查通过后只提交一条 MP4 草稿。A/B、实际源起止、成片时长和结束原因分别记录，录制路线记为 `tabCapture-to-canvas`。
- 只有助手确认存在素材条目才显示已保存，并清理浏览器暂存；缓存清理失败不能反过来把已经存在的 MP4 报为保存失败。上传或转码失败保留原始块，草稿页提供“重试保存 MP4”。
- 已收齐并记录实际结束范围的任务可以重试；浏览器在录制中被强制关闭而没有可靠结束范围时，仅保留已落盘数据并显示错误，目前不能承诺自动恢复为完整成片。

- 42 项前端逻辑检查通过，包含录制器先于源播放、准备取消、并发停止合并、旧状态不能影响新任务、确认丢失重放、转换失败保留与免重传重试、缓存清理失败仍保存成功、裁剪和实际状态条尺寸回归。
- 格式、类型、生成脚本检查及生产构建通过。一次总检查在构建阶段遇到 Node 内存不足；逻辑检查已通过，随后单独重跑完整构建和生成脚本检查成功，没有将首次命令写为成功。
- 15 项原生文件/协议检查通过。生产 TypeScript 上传代码连接真实新助手进程和 FFmpeg，使用自制两秒 WebM 验证丢失确认重放与幂等提交，产出 H.264/AAC、640×360、2 秒 MP4；独立解码得到 60 个视频帧、94 个音频帧。这是文件管线集成检查，不是 tabCapture 实测。
- 用户关闭试验扩展并重新加载正式扩展，随后为正式扩展绑定 Ctrl+Shift+9。YouTube A=2、B=4 的真实首次命令报“录制状态条会遮住视频”，没有开始正常采集；失败后预览恢复到 B，与用户所见一致。
- 布局回归先在实际 `videoCapture.prepare` 调用处失败，再修正；真实浏览器夹具的相同顶部空间条件也先失败。修正后测得状态条高 54、顶部 6、底部 60，视频顶部 68，准备检查通过。没有绕过交叠检查，也没有用该布局检查冒充开始录制。
- 修正版已取得三个实际文件，详情见下方。三站完整采集矩阵、采集时序精度、旧停帧的自制时钟冷启动/重复采集、正式安装包仍未通过。

## 2026-10-23：采集时长优化

原自动停止样本实际源区间为 2.046655 秒，MP4 容器为 2.554333 秒，额外 0.507678 秒，未通过本轮 0.12 秒比较门槛。对上方 75% 画面做统一尺寸灰度比较，原片约 0.533 秒才出现明显变化，额外时长主要表现为开头停留在 A 附近。代码同时存在等待异步 start 事件、等待录制状态持久化和通知的串行步骤。

新增生产协调器与录制启动函数的联动回归：模拟 start 事件晚到 500 ms、每次状态存取/通知各 100 ms，原逻辑出现 700 ms 源播放等待；修复后开始等待不超过 50 ms、总余量不超过 100 ms。43 项前端检查（录制相关 13 项）、格式、类型、正式构建与生成脚本检查通过。默认 fork 首次启动失败，未执行测试；改用 threads、单 worker 完成上述检查。初次类型检查的状态窄化错误已修正，最终构建通过。

用户重新加载后，用同一真实页面、A=2、B=4，再按一次 Ctrl+Shift+9，自动停止并显示“已存入草稿箱”。新素材实际源区间为 2～4.032694 秒，MP4 容器 2.133333 秒，额外 **0.100639 秒**，通过本轮比较门槛；最大编码轨道 2.121333 秒。H.264 视频 63 帧、AAC 音频 100 帧，完整解码与说明哈希一致性通过，音频 RMS 为 -25.550672 dBFS。抽帧持续变化，没有观察到桌宠、选段窗或原生控制条；网页字幕保留。

新片首张画面与原片 A 附近图像接近，并未呈现原片 A 后约半秒的画面；明显画面变化提前到约 0.133 秒。这支持减少了开头等待，没有通过裁掉约半秒内容来凑时长，但仍不是逐帧边界证明。没有修改转换器、强制输出时长或改写原三个文件。0.12 秒仅是本轮对照门槛，不承诺所有平台和性能条件都在该范围内；实际终点与 B 仍分别记录。新结果见 [时长证据](evidence/recording-timing-2026-10-23.json)，原始三路径结果仍保留在上方及原证据中。

## 2026-10-23：后续时长波动与停止确认往返优化

在不修改既有文件的条件下重查 `3113c31e…`，实际源区间 16.034096 秒、容器 16.185333 秒，余量 0.151237 秒，仍未通过 0.12 秒门槛。视频轨道 16.100000 秒，音频轨道自 0.025000 秒开始、时长 16.160333 秒。自制两秒 WebM 按相同转换参数输出两秒 MP4，没有额外拉长；这只排除了该对照中的转换膨胀，不能代替已清理的真实原始 WebM 分析。

已暂停的源页面原先先发停止通知，再由后台回问 `capture-finish`、等回复后停止录制器。现在源身份有效且已暂停时，停止通知一起携带实际源时间 `pausedAt`，先清理本地帧回调与进度轮询。后台只从当前源标签、匹配任务接收该时间；协调器仅使用实际起点之后的有限值，其他情况保留原确认流程。手动快捷键、按钮和关闭模式的确认流程保持现有实现；不改 Canvas 路线、不增加编码依赖，也没有通过裁剪旧文件调整结果。

两个回归在修复前失败：120 ms 页面回复延迟会阻挡停录、实际帧结束通知没有带回已暂停时间。修复后通过，完整前端检查为 45 项（录制相关 15 项），格式、类型、正式构建和生成脚本检查通过。真实改进幅度仍待重新加载后的新自动停止录像验证，不能凭模拟检查宣称既有精度失败已解决。见 [停止时序证据](evidence/recording-jitter-2026-10-23.json)。
