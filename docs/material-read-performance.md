# 大图分块读取优化

更新日期：2026-10-24。状态：代码、原生回归、实际助手规模测量和正式构建通过；用户已确认重新加载后，正式扩展右侧正常显示彩色测试图，实际文件及当前助手指纹另行核对通过。上传恢复的部分原文件补选已另外验收通过。

## 发现的问题与修正

交付前性能检查用自制素材构成 100、500、1,500 条的独立库。1,500 条底库加入一张 4,334,289 字节 PNG 后，完整读回需要 23 个请求，总耗时约 16.30 秒；每个请求都接近一次完整列表扫描的耗时，包括最后不足一个整块的请求。

原实现的 `ReadFile → Find → List` 每读 192 KiB 都遍历全部素材。浏览器拼接一张图片因此重复读完整库的说明文件。100 条素材的较小复现同样触发了读取规模检查失败，图片字节仍正确；这不是图片解码分支。修正只调整连续分块的定位，不改上传、录制或素材文件格式。

现在每次新读取、重读或跳读仍通过原定位流程。同一附件紧接着的下一个分块可以复用本次读取已经定位的目录；每块仍核对素材 ID、说明版本、附件文件名、长度和修改时间，并执行原路径检查。来源、说明或目录在连续读取中改变时中止，重新从 0 开始可再次定位。不同目录和不同库分开处理，写入和转移操作继续使用原完整定位检查。

定位信息最多保留 16 份，10 秒未继续使用后失效，读完或出错即移除。请求之间不保留文件句柄、媒体字节或整个素材对象，不新增数据库、依赖或协议字段。

## 测量结果

以下是本机两次隔离助手测量，自制媒体内容和库规模相同；不是正式浏览器显示时间，也不代表通用耗时保证。首批新文件与助手启动时间另外记录，没有清空操作系统磁盘缓存。

| 项目 | 原助手 | 修正版 |
| --- | ---: | ---: |
| 100 条底库，大图完整读回 | 2,872.467 ms | 145.934 ms |
| 1,500 条底库，大图完整读回 | 16,296.999 ms | 809.188 ms |
| 1,500 条底库，分块请求中位耗时 | 700.616 ms | 3.077 ms |
| 1,500 条底库，列表读取中位耗时 | 730.057 ms | 718.530 ms |

新旧图像均由 23 块完整读回，与原文件 SHA-256 一致。修正后第一块仍要定位，1,500 条场景为 733.990 ms；其余各块通常约 3 ms，符合只定位一次的预期。列表扫描本身保持原实现，不将同样约 0.7 秒的结果算作已解决。

100 条的专用诊断命令以「4 次列表中位耗时加 250 ms」作为相对检查预算，捕捉每块都扫描整库的问题，不是产品响应时间标准。原版本为 2,872.467 / 455.576 ms，失败；修正版为 145.934 / 442.720 ms，通过。原始失败与全部测量报告保留在本地证据中。
